# 0009 Segundo fator por aplicativo autenticador para diretor e financeiro

**Contexto.** Quem obtém a senha de um diretor ou financeiro lê o caixa de todas as obras do tenant e usa o assistente (achado SEG-01). O plano, seção 4.1 item 3, exige TOTP do Supabase Auth com nível `aal2` para esses perfis; gerente de obra, comercial e leitura seguem em `aal1` no MVP. A documentação do Supabase diz que a API de TOTP é gratuita e vem ligada em todo projeto; o que precisa estar ligado é a opção no Dashboard e as chaves `[auth.mfa.totp]` do `config.toml`.

**Decisão.** A regra fica numa função pura, `decidirDestino` em `painel/lib/supabase/nivel-acesso.ts`, lida do JWT (`app_metadata.perfil` e `aal` via `getClaims`) sem consulta a tabela. O proxy redireciona para `/seguranca/segundo-fator/cadastrar` ou `/verificar` e o layout do painel repete a checagem com `getUser` e `getClaims`, porque proxy sozinho não protege rota. As telas ficam fora do grupo `(painel)` para serem alcançáveis em `aal1`. Cadastro (`mfa.enroll` com QR em SVG, `challenge` e `verify`) e verificação (`challengeAndVerify`) rodam em Server Actions; o token `aal2` vai para o cookie pelo `setAll` do cliente servidor no evento `MFA_CHALLENGE_VERIFIED`. Quem já tem fator verificado e está em `aal1` não consegue cadastrar outro: a senha roubada bastaria para trocar o celular. Um aparelho por usuário no MVP.

**Consequência.** O limite de tentativas do código é o rate limit do Supabase Auth (erro 429 vira mensagem de espera); não há contador próprio. Perda do celular é resolvida pelo administrador removendo o fator (`docs/operacao/segundo-fator.md`). Códigos de recuperação e passkey ficam para depois do piloto. As políticas de RLS continuam sem checar `aal`; se um perfil precisar bloquear dado em `aal1` mesmo fora do painel, a política restritiva por `aal` da documentação entra numa migration nova.
